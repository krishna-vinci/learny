# M2 Cards & Review Implementation Plan

> **For agentic workers:** Execute only the task you were given. Do not load brainstorming or other workflow skills. Read `/path/to/studium/AGENTS.md` first. If a step does not fit the real code or a library API differs from what is written here, stop and report the mismatch (file:line, what you saw) instead of improvising. Run biome as `rtk proxy pnpm exec biome check <files>` (without `rtk proxy` a shell hook fakes an "out of memory" crash when biome finds problems; if `rtk` is missing, run biome directly).

**Goal:** From any accepted chapter, the learner gets flashcards drafted by a Cardsmith and filtered by a Critic against SuperMemo's 20 rules and the existing deck; reviews them quickly on a phone; exports approved cards as an `.apkg` (imports cleanly into AnkiDroid / AnkiMobile / desktop Anki, updates instead of duplicating on re-import) or syncs them to desktop Anki via AnkiConnect; quizzes in chat with results logged; and sees which cards went stale after a note changed.

**Architecture:** Cards live in `<set>/cards/NN-slug.md` (format in `docs/STUDY_TREE.md`), parsed/serialized by `shared/src/cards.ts` so server and web agree. A `make-cards` job (M1 job runner) runs Cardsmith → Critic with ≤2 retry rounds, reusing the M1 role system. Card mutations from the UI are user commits. Anki export is a pure `.apkg` writer on `sql.js` (no native deps). AnkiConnect is spoken directly (every Anki MCP server wraps AnkiConnect anyway): browser → `localhost:8765` on desktop by default, server → `ANKICONNECT_URL` when set. Agents never write to Anki (P4, D15).

**Tech Stack:** M1 stack + `sql.js@^1.14.2` (+ `@types/sql.js`), `jszip` (already present) for the `.apkg` container.

**Spec:** `docs/REVIEW_LOOP.md` (D16), `docs/STUDY_TREE.md` (cards format), `docs/AGENT_ROLES.md`, `docs/PRINCIPLES.md` (P4, P10), `docs/decisions/LOG.md` (D3, D16, D19, D22), M1 plan conventions.

## Global Constraints

- All M1 constraints apply (tests without network/LLMs, faux provider, pinned Pi, per-role write policies through `tree/edit.ts`, one GLM run at a time, mobile-first UI verified by screenshot).
- **Card ids are forever:** `c-` + 8 lowercase hex (random), never regenerated; the Anki note GUID is exactly the card id (D16). Changing either duplicates the learner's cards — high-risk area.
- Agents never call AnkiConnect or produce `.apkg` files; export and sync are user actions from the UI.
- Card text is Markdown with `$…$` / `$$…$$` math; conversion to Anki MathJax `\(…\)` / `\[…\]` happens only at export.

## Decisions (fixed)

1. **Card file format** (extends `docs/STUDY_TREE.md`):
   ```md
   ---
   deck: Linear Algebra::SVD        # default: <PLAN title>::<note title>
   note: notes/03-svd.md
   note_sha: <git blob/commit sha of the note the cards were last made or reviewed against>
   ---

   ## c-8f3a1b2c
   <!-- status: approved · type: basic · anki: 1712345678 · src: lib-strang-la#p364 · critic: ok -->
   **Q:** …
   **A:** …

   ## c-91bd07e4
   <!-- status: rejected · type: cloze · critic: rule 4 (too many facts) -->
   **Text:** The SVD factors $A$ into {{c1::$U\Sigma V^\top$}}.
   **Extra:** …
   ```
   Statuses: `draft | approved | rejected | exported`. Types: `basic | cloze`. Comment keys are optional except `status` and `type`. `stale` is derived, never stored.
2. **Roles** added to `ROLES`: `cardsmith` (read set notes + library; write only `<set>/cards/**` via a job-specific path like the M1 Drafter pin: exactly the target cards file) and `critic` (read; may only set per-card status/critic fields through a dedicated tool `review_card {id, verdict: "ok" | "reject", rule?: number, reason?: string}` that edits exactly that card's comment line). Model roles `cardsmith`, `critic` already exist in config.yaml.
3. **Skills:** `make-deck` (card types, minimum-information principle, one fact per card, cloze for enumerations, context cues, no orphan pronouns, source citation in `src`) and `critique-cards` with `references/twenty-rules.md` — a faithful **paraphrase** (not a verbatim copy) of Piotr Woźniak's "Effective learning: Twenty rules of formulating knowledge" (SuperMemo, 1999), numbered 1–20, with attribution and link, plus Studium's interference check (flag a card whose question is near-identical to an existing approved/exported card in the set; include the other card id).
4. **`make-cards` job** input `{ set, note: "notes/NN-slug.md", count?: number (default 12, max 40) }`: target file `cards/NN-slug.md` (created if missing; existing approved/exported cards are kept and shown to both agents as "existing deck"). Cardsmith appends new `draft` cards (fresh ids generated by the tool, not the model). Critic reviews each new card; rejected cards get one Cardsmith revision round (edit in place, same id) and a re-review; after ≤2 rounds remaining rejects stay `rejected` with the reason. Critic-clean cards stay `draft` with `critic: ok` (the learner approves — P10). Commits: cardsmith / critic authors, paths pinned. Updates `note_sha`.
5. **Card id generation** is server-side in the `add_card` tool (`add_card {type, q?, a?, text?, extra?, src?}` → returns the id); the model never invents ids.
6. **Stale:** a card file is stale when the note's current commit sha for that path differs from `note_sha`; the API reports `stale: true` per file and lists the note commits since. "Re-check" = a `make-cards` job with `count: 0` (Critic-only review of existing cards against the updated note).
7. **`.apkg` writer** (`server/src/anki/apkg.ts`): legacy Anki 2.1 collection (`collection.anki2`, schema 11) built with `sql.js`: tables `col` (with `models` JSON for note types `Studium Basic` (fields Front, Back, CardId, Source, NoteLink; one template) and `Studium Cloze` (fields Text, Extra, CardId, Source, NoteLink; cloze type)), `notes` (`guid` = card id, `mid`, `flds` joined by `\x1f`, `sfld`, `csum` = first 8 hex of sha1(sfld) as int), `cards` (one per basic note; one per cloze ordinal), `revlog` empty, `graves` empty; `decks` JSON with `Studium::<set>::<NN-chapter>` hierarchy; zipped with `media` = `{}` (or the media map when images are included). Note type ids and deck ids are stable (derived from a hash of their names) so re-imports update existing notes. Field content: card Markdown → HTML (use the existing markdown pipeline on the server side: a small `marked`-free converter is fine: paragraphs, bold/italic, code, lists) with `$…$` → `\(…\)`, `$$…$$` → `\[…\]`; Source field = source title + locator; NoteLink = `studium://…` not needed — use the app URL if `STUDIUM_BASE_URL` is set, else the note path text.
8. **Export API:** `GET /api/sets/:set/export.apkg?cards=approved|approved+exported&note=<path?>` → `application/octet-stream` download named `studium-<set>.apkg`; on success the server marks included `approved` cards `exported` (user commit). Re-exporting `exported` cards is allowed (updates in Anki).
9. **AnkiConnect** (`shared/src/ankiconnect.ts`, usable in browser and server): `version`, `deckNames`, `createDeck`, `findNotes("CardId:<id>")`, `addNotes`, `updateNoteFields`, `modelNames`, `createModel` (creates the two Studium note types if missing — same field names as the .apkg). Server route `POST /api/sets/:set/anki/sync` only when `ANKICONNECT_URL` is set; the web uses the browser client against `http://localhost:8765` on desktop (after a `version` probe) and posts results back via `POST /api/sets/:set/cards/exported {ids, ankiIds}` so card files record `anki: <noteId>` and `status: exported`.
10. **Quiz:** skill `quiz-me` (ask one question at a time from notes/cards, wait for the answer, grade right/partial/wrong with a one-line why, adapt difficulty, offer to add/revise a card or note on misses — offers only, P10) + Tutor tool `record_quiz_result {topic, question, verdict: "right"|"partial"|"wrong", gap?}` appending a line to `<set>/log/quiz.md` (user-invisible append allowed for the Tutor: extend its write policy to exactly that file). No special quiz UI in M2 — it runs in the chat.

## API (additions; types in `shared/src/api.ts`)

| Method & path | Request | Response |
|---|---|---|
| `GET /api/sets/:set/cards` | — | `CardFileView[]` = `{ path, note, deck, stale, noteCommitsSince: number, counts: Record<CardStatus, number> }` |
| `GET /api/sets/:set/cards/file?path=cards/NN-slug.md` | — | `{ path, note, deck, stale, cards: CardView[] }` |
| `PATCH /api/sets/:set/cards/:id` | `{ status?: "approved" \| "rejected" \| "draft", q?, a?, text?, extra? }` | `200 CardView` (user commit) |
| `POST /api/sets/:set/cards/approve-clean` | `{ path }` | `200 { approved: number }` (all `draft` with `critic: ok`) |
| `POST /api/sets/:set/cards/exported` | `{ ids: string[], ankiIds?: Record<string, number> }` | `200` |
| `GET /api/sets/:set/export.apkg` | query per decision 8 | file download |
| `POST /api/sets/:set/anki/sync` | `{ path? }` | `200 { added, updated, failed: {id, error}[] }` (only with `ANKICONNECT_URL`) |
| `POST /api/jobs` | `{ kind: "make-cards", set, note, count? }` | `202 { jobId }` (Tutor `start_job` can propose it too) |

`CardView = { id, type: "basic" | "cloze", status, q?, a?, text?, extra?, src?, critic?: { verdict: "ok" | "reject"; rule?: number; reason?: string }, ankiId?: number }`.
