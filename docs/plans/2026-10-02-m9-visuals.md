# M9 — Visuals that teach: widgets, a sketch runtime and stories

**Goal:** visuals look like part of Studium, start on their own, can be stepped through scene by scene, and always have a static form for the PDF book. Agents get a high-quality floor: built-in widgets for the common cases, and a bundled drawing runtime for everything else.

**Builds on (read first):** D29 (media in notes), **D31 (Visuals tab — already shipped: placement is decided, don't redo it)**, M7 report (`docs/plans/2026-10-01-m7-media-report.md`), chapter-visuals report (`docs/plans/2026-10-02-chapter-visuals-report.md`), `shared/src/media.ts` (`chapterVisuals()`), `web/src/components/Reader/{ChapterVisuals,ArtifactBlock,VegaLiteBlock}.tsx`, `server/src/jobs/book-media.ts`, `skills/media-authoring/`, `docs/TEACHING.md`.

## Fixed decisions
- **V1 One directive, one folder.** New visuals live in `<set>/visuals/` and are declared at chapter level with `::visual{src="../visuals/<name>.json|.html" title="…"}` (same collection rules as D31: standalone leaf, chapter level, collected by `chapterVisuals()`, shown only in the Visuals tab). `.json` = widget spec, `.html` = sketch. `::artifact{…}` and `artifacts/` keep working unchanged (alias, no migration of user files). Agents write new ones only in `visuals/`. Add `visuals/` to the agent write scope exactly like `artifacts/` (paths.ts, roles, draft-job media allowance, size caps).
- **V2 Widgets are pure functions + thin React.** For each widget: a zod spec schema and a pure `layout(spec, state) → scene` (SVG node tree) in `shared/src/visuals/<widget>.ts` (d3 used only for scales/shapes/math, no DOM); a React component in `web/` renders the scene as SVG and adds controls; the server renders the same scene to an SVG string for the book (no browser, no React on the server). One source of truth for both media.
- **V3 First widget batch** (chosen from the real chapters: linear algebra, PCA, polymers, Hyderabad history, an AI-model explainer):
  1. `function-plot` — one or more `y = f(x; params)` curves, sliders for params, axes with labels and units, optional marked points. Expressions parsed by the safe evaluator (V9).
  2. `matrix-transform` — a 2×2 (optionally 3×3 shown as 2-D projection) matrix applied to a grid, unit circle and basis vectors, animated from identity; optional SVD mode that plays V^T → Σ → U as three scenes.
  3. `step-through` — an algorithm/process animator from a JSON trace: an array/list, a small graph or a stack of labelled boxes per step, with a caption per step (sorting, attention/n-gram lookup, polymerisation steps, a pipeline).
  4. `timeline` — events and eras on a zoomable axis with categories and a selected-event card (dates as years or ISO dates; BCE allowed).
  Each spec has `title`, optional `caption`, `story?: {scenes:[{state, narration}]}` (V5) and is validated on agent write (tool error with the zod message, so the agent fixes it).
- **V4 Sketch runtime, served not inlined.** `web/public/visual-runtime/` (built, content-hashed, immutable cache, **no auth** — public static libraries only) holds `p5`, `d3`, `three` (lazy) and `studium-runtime.js` (controls kit, theme, story engine, poster export). A sketch declares its needs in a header: `<script type="application/json" id="studium-visual">{"libs":["p5"],"story":true,"aspect":"16:10"}</script>`. The parent builds `srcDoc` = CSP meta + runtime `<script src>` tags for exactly the declared libs + the sketch. CSP: `default-src 'none'; script-src 'unsafe-inline' <location.origin>/visual-runtime/; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`. The iframe stays exactly `sandbox="allow-scripts"` (opaque origin, so cookies/session never reach it). Never inline megabytes of library text into srcDoc.
- **V5 Stories.** A visual (widget or sketch) may declare ordered scenes, each with one narration sentence. The runtime chrome shows: play/pause, a scrub bar, prev/next, scene dots, the narration line, and keyboard ←/→/space. Widgets get the same chrome in React. **Scroll-synced scrollytelling is deferred** (janky on phones, conflicts with the Visuals list scroll); record it in the decision as future work.
- **V6 Autoplay, politely.** Visuals start when ≥ 50 % visible in the Visuals tab, pause when off-screen or the page is hidden, and stop/unmount per D31 when leaving the tab. `prefers-reduced-motion`: start paused on scene 1, no auto-advance. At most one sketch animates at a time on phones (the most visible one). No Run button for sketches/widgets (legacy `::artifact` keeps its Run button: unknown code, unknown cost).
- **V7 Theme inheritance.** The parent sends `{bg, fg, muted, accent, grid, font, palette, dark}` to the frame by `postMessage` at load and on theme change (target origin `"*"` is fine: the payload is non-sensitive design tokens; the parent accepts **no** messages from frames except `{type:"studium-visual", event:"ready"|"error"|"scene", …}` with shape validation). Palette = Okabe-Ito (colour-blind safe), mapped to the 5 themes' contrast. Font = the app's system font stack (no webfonts in the frame). Widgets read the same tokens directly.
- **V8 Book contract** (record in LOG as D32): widget → server-rendered SVG of its default state, plus one SVG per story scene with its narration as caption (max 6 scenes; beyond that, first/last + "N more in Studium"); sketch → its `poster` SVG (required for new sketches) or `posters: [...]` per scene when it declares a story; no poster → title + "open this chapter's Visuals tab in Studium" (D31 behaviour). Never run HTML or a browser for the book. Optional headless capture stays deferred with Mermaid→SVG (needs Chrome).
- **V9 Dependencies (exact pins, lazy):** `p5`, `d3`, `three` (served as runtime files; widgets import only d3 submodules they need via `d3`), and a math-expression parser. **Check `expr-eval` 2.0.2 first:** it is unmaintained since 2022 and has had code-execution advisories; if `pnpm audit`/GitHub advisories flag it, use the maintained, patched fork (e.g. `expr-eval-fork`) or an equivalent safe evaluator, and justify it in the report. The evaluator must allow only arithmetic, whitelisted functions (sin, cos, exp, log, sqrt, abs, pow, min, max, floor, ceil) and declared variables — no member access, no assignment, no function definitions. Fuzz-test that. Nothing else without justification.
- **V10 Router slot.** `server/src/agent/visual-router.ts`: `interface VisualRouter { decide(section: {heading, text, subject}): Promise<{want: boolean; form?: "widget"|"sketch"|"chart"|"none"; widget?: string} | null> }`; default `nullRouter` (returns null → the skill's own judgement applies). Config flag `visuals.router: off` in `_global/config.yaml` schema (default off). Not wired to any model (the Jev spike may later fill it). Mention it in the skill and LOG.
- **V11 Skill = single source of truth.** New `skills/make-visual/` (SKILL.md ≤ 150 lines + `references/`): when a visual earns its place (one concept per visual; prose must stand alone), decision table widget vs sketch vs Vega chart vs Mermaid vs SVG figure, the widget catalog with full spec examples, the sketch runtime API, cheat-sheets `p5.md`, `d3.md`, `three.md` (only the APIs agents need, version-pinned), the quality bar (autoplay, labelled axes with units, Okabe-Ito palette via `studium.palette`, readable at 360 px, touch, reduced motion, scrubbable time where meaningful, ≤ 300 KB), the poster rule (V8), and the router note (V10). `media-authoring` keeps images/YouTube/Mermaid/Vega and points to `make-visual` for everything interactive; `draft-chapter`, `explain`, `evolve-note` point to it. Register via `scripts/skill-history.mjs` and format the JSON with biome.
